> [!quote]- Resumen
> # Guía Integral para la Presentación Final: Desarrollo de Sistemas y Bases de Datos
> 
> Este documento constituye un recurso académico exhaustivo diseñado para orientar a los estudiantes en la preparación, ejecución y defensa del Trabajo Práctico Integrador de la materia. Contiene directrices técnicas, pedagógicas y organizativas fundamentales para asegurar el éxito en la instancia final de evaluación.
> 
> ## 1. Introducción General
> 
> El cierre del cuatrimestre se articula en torno a una presentación final que no solo evalúa el conocimiento técnico adquirido, sino también la capacidad de comunicación profesional en un nivel terciario. El proyecto final representa el trayecto completo de desarrollo, desde el análisis de requerimientos iniciales hasta la implementación de consultas complejas en una base de datos funcional.
> 
> ## 2. Marco Conceptual y Definiciones Clave
> 
> Para abordar la presentación con solvencia, es imperativo dominar los siguientes conceptos que estructuran el desarrollo del proyecto:
> 
> - **DER (Diagrama Entidad-Relación):** Es el modelo conceptual que representa la estructura lógica de la base de datos. Es el punto de partida que traduce la "papeleta" (requerimientos) en una arquitectura de datos.
> - **DDL (Data Definition Language):** Se refiere a los comandos SQL (como `CREATE`, `ALTER`, `DROP`) utilizados para definir la estructura de la base de datos, incluyendo tablas, campos y relaciones.
> - **Consultas (Queries):** Sentencias de manipulación de datos utilizadas para extraer información específica. Se enfatiza el uso de funciones de agregación y formato.
> - **Alias y Concatenación:**
>     - `**CONCAT**`**:** Función utilizada para unir dos o más cadenas de texto en los resultados de una consulta.
>     - **Alias con Comillas:** Uso de comillas (ej. `"Nombre de Columna"`) cuando el alias de un campo contiene espacios o caracteres especiales, mejorando la legibilidad del reporte.
> - **Entorno de Ejecución (XAMPP):** Paquete de software que incluye el servidor de base de datos MariaDB/MySQL necesario para demostrar el funcionamiento del sistema en tiempo real.
> 
> ## 3. Desarrollo del Tema: La Presentación Final
> 
> La evaluación se centra en la capacidad del grupo para demostrar un flujo de trabajo coherente y profesional.
> 
> ### Estrategias de Comunicación (El Enfoque de "Venta")
> 
> El equipo debe decidir, bajo su propia creatividad, qué rol asumirá frente al interlocutor (el docente):
> 
> 1. **Enfoque Técnico (Recruiter/Gerente de Sistemas):** Una presentación de igual a igual, utilizando terminología avanzada y defendiendo las decisiones de arquitectura y código como una "prueba técnica".
> 2. **Enfoque Comercial (Cliente/Dueño de Club):** Una presentación orientada a la solución de problemas de negocio, explicando cómo el sistema beneficia al usuario final, matizando la teoría para que sea comprensible para un no experto.
> 
> ### El Proceso de Explicación
> 
> La defensa debe seguir una secuencia lógica que refleje el desarrollo real del software:
> 
> 1. **Análisis de Requerimientos:** Lectura e interpretación de la "papeleta" inicial.
> 2. **Modelado:** Explicación del DER y cómo se llegó a esa estructura.
> 3. **Implementación:** Muestra del DDL y la creación de la base de datos.
> 4. **Resultados:** Ejecución y explicación detallada de las consultas realizadas.
> 
> **Resumen Parcial:** La presentación es un acto de "venta" donde la prolijidad visual y la seguridad discursiva son tan importantes como el código subyacente.
>

>

> 
> ## 5. Errores Comunes y Advertencias
> 
> El docente ha identificado puntos críticos que pueden perjudicar la nota o la regularidad:
> 
> - **Uso de IA (ChatGPT):** Si se detecta un salto de calidad inexplicable o "sofisticado" sin fundamento, se procederá a una indagación técnica profunda ("punzón oxidado"). Si el alumno no puede explicar su código, la evaluación será negativa.
> - **Falta de Preparación Oral:** Leer de papeles o tartamudear demuestra falta de dominio. Se espera "parleta" y seguridad.
> - **Ausentismo:** La presencia es obligatoria para todos los integrantes. La ausencia en la presentación, sumada a un parcial insuficiente, resulta en la pérdida de la regularidad y la obligación de recursar.
> - **Descuido Visual:** No subestimar la estética. Una buena interfaz o presentación puede predisponer positivamente al evaluador.
> 
> ## 6. Síntesis y Conclusiones
> 
> El éxito en esta instancia depende de la integración de tres pilares:
> 
> 1. **Contenido Sólido:** Un DER y consultas SQL correctamente fundamentadas.
> 2. **Estética Profesional:** Una presentación visualmente atractiva ("uno compra por la vista").
> 3. **Defensa Oral:** Capacidad de explicar el "porqué" de cada decisión técnica.
>

> ## 8. Preguntas de Repaso
> 
> ### Nivel Básico
> 
> 1. ¿Cuál es la función principal del DER en el inicio de un proyecto de base de datos?
> 2. ¿Por qué es necesario usar comillas en los alias de las consultas SQL?
> 3. ¿Qué herramientas de software deben estar operativas antes de comenzar la presentación?
> 
> ### Nivel Intermedio
> 
> 4. Explique la diferencia entre presentar el proyecto a un "Recruiter" versus un "Dueño de Negocio". ¿Cómo cambia el lenguaje técnico en cada caso?
> 5. ¿Qué importancia tiene la función `CONCAT` en la mejora de la visualización de los datos para el cliente?
> 6. ¿Qué consecuencias académicas tiene la ausencia injustificada el día 27 de septiembre?
> 
> ### Nivel Avanzado
> 
> 7. Si un grupo decide utilizar una estructura de código muy sofisticada (posiblemente asistida por IA), ¿qué debe demostrar durante la indagación del profesor para no reprobar?
